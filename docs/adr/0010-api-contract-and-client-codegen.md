# ADR-0010: API contract and client codegen

- Status: Accepted
- Date: 2026-11-17

## Context
The backend and frontend must agree on one contract, and that contract must be impossible to drift silently. No CI exists (ADR-0001), so drift checks must be local make targets. Research (`docs/research/codegen-and-frontend-testing.md`) compared generators.

## Options considered
**Source of truth**
- Hand-written OpenAPI: drifts from the code.
- **FastAPI-generated** from the Pydantic models in `models.py`: the code is the spec. Chosen.

**Client generator**
| | openapi-typescript + openapi-fetch | orval | @hey-api/openapi-ts |
|---|---|---|---|
| Output | a types-only `.d.ts`, no generated runtime | per-operation functions, optional mocks | generated client and SDK files |
| Runtime | about 6 kB | depends on the client | small generated client |
| OpenAPI 3.1 | documented | not confirmed | not confirmed |
| Typed errors | yes (`error` from 4xx/5xx/default) | not verified | claimed |
| Drift check | built-in `--check` | none built-in | none verified |
| Mocking | `openapi-msw` typed handlers | built-in MSW + faker | hand-written |
| Maturity | stable | very active | pre-1.0, pin exactly |

**Chosen: openapi-typescript + openapi-fetch.** It has the least generated code to review, a built-in `--check`, and typed MSW handlers (ADR-0011). Orval's auto-generated mocks are more machinery than one GET endpoint needs.

## Decision
- `openapi.json` is exported by `python -m telescope.export_openapi` (`make openapi`): `json.dumps(app.openapi(), indent=2, sort_keys=True)` + newline, so it is deterministic. It is **committed at the repo root**, so both stacks read the same file.
- `frontend/src/api/schema.d.ts` is generated by `pnpm gen:api` and committed, with `src/api/client.ts` wrapping `createClient<paths>`. `make gen-client` runs both steps.
- Pydantic's default `separate_input_output_schemas=True` is kept (precise response types: fields with defaults are required in the output).
- **problem+json post-processing**: FastAPI documents error responses as `application/json`, so the app's `openapi()` is post-processed to advertise `application/problem+json` with the `Problem` schema for 4xx/5xx. This lets `error` in `openapi-fetch` be typed as a problem document (research flagged this as unverified; the architect verified it: the generated `schema.d.ts` types 4xx/5xx as `"application/problem+json": components["schemas"]["Problem"]`, and `pnpm gen:api:check` keeps it in sync).
- **Drift checks**, both local:
  1. pytest (`test_openapi_contract.py`): `render() == committed openapi.json`, so changing a model without running `make openapi` fails `make test`.
  2. `pnpm gen:api:check` (inside `make lint`): `schema.d.ts` must match `openapi.json`.
  Together: code -> `openapi.json` -> `schema.d.ts`, with each hop checked.
- The frontend calls only our backend through the typed client. It never talks to GitHub.

## Consequences
- Pro: one source of truth, a typed end-to-end contract, and a failing check on any drift, including at review time.
- Pro: client code is a 6 kB runtime plus a `.d.ts`, with no generated logic to maintain.
- Con: a contract change needs two commands (`make gen-client`) plus committing two generated files. The checks make forgetting loud rather than silent.
- Con: `schema.d.ts` is not a runtime validator: responses are trusted, not parsed. That is acceptable because both ends are ours and tested against the same spec. Schemathesis (ADR-0011) can probe the server side.
- Con: `sort_keys` ordering and library versions affect output, so FastAPI/Pydantic upgrades will produce spec diffs to review.
- Con: the post-processing is a small hack over FastAPI's OpenAPI generation. It is isolated in one function and covered by a test.
